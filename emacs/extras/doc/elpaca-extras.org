This manual describes the features and customization options for the Emacs Lisp file =elpaca-extras.el=.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=elpaca-extras.el= extends the =elpaca= package manager with commands that make it easier to iterate on packages without restarting Emacs. When you update or rebuild a package, its old definitions remain loaded in the running session. These extensions automate the tedious process of force-loading updated features, and they also provide filtered lock-file writing.

The main capabilities are:

- *Reload after update.* A command that updates a package and automatically reloads its features once the build finishes ([[#h:update-and-reload][Update and reload]]).
- *Reload after rebuild.* The same workflow for package rebuilds ([[#h:rebuild-and-reload][Rebuild and reload]]).
- *Manual reload.* A standalone reload command for when you have made local edits to a package's source ([[#h:reload][Reload]]).
- *Package resolution.* Mapping package IDs, checkout names, and source files to one queued package ([[#h:package-resolution][Package resolution]]).
- *Filtered lock files.* Writing Elpaca lock files while excluding specific packages ([[#h:lock-file][Lock file management]]).

** ~elpaca-extras-write-lock-file-excluded~
:PROPERTIES:
:CUSTOM_ID: h:elpaca-extras-write-lock-file-excluded
:END:

#+vindex: elpaca-extras-write-lock-file-excluded
The user option ~elpaca-extras-write-lock-file-excluded~ specifies a list of package identifiers (symbols) that should be omitted when writing a lock file with ~elpaca-extras-write-lock-file-excluding~ ([[#h:lock-file][Lock file management]]). This is useful for packages that are installed from local sources or that you do not want pinned to a specific revision.

The default value is ~nil~ (no exclusions). The type is a list of symbols.

* Package resolution
:PROPERTIES:
:CUSTOM_ID: h:package-resolution
:END:

#+findex: elpaca-extras-resolve-package
The function ~elpaca-extras-resolve-package~ maps an Elpaca package ID, package name, source-directory basename, or absolute source path to a plist containing the canonical package ID, package name, source directory, and checkout label. Exact IDs take precedence. A main source filename can distinguish packages that share one checkout. Any remaining ambiguity signals an error instead of selecting an arbitrary package.

** Reload
:PROPERTIES:
:CUSTOM_ID: h:reload
:END:

#+findex: elpaca-extras-reload
After making local edits to an installed package or after a manual rebuild, the old feature definitions remain active in the running Emacs session. The command ~elpaca-extras-reload~ force-loads the features provided by a specified package so new definitions replace old ones.

It works by reading the package's =.el= files, extracting every feature name and direct dependency from their ~provide~ and ~require~ forms, and loading each selected source or compiled artifact once. The main feature retains its established first-load position; package subfeatures are then loaded after the subfeatures they require. This dependency order keeps unchanged EIEIO class hierarchies coherent during reload. Before loading, the command compares statically visible classes' direct parent sequences and effective instance-slot vectors with the selected definitions. The static scan walks every executable top-level form cons by cons, so improper lists such as the dotted destructuring pattern of a ~cl-loop~ clause are traversed rather than rejected, which is what lets Elpaca itself be reloaded. It refuses a selected file when that file previously created a class whose declaration cannot be inspected. A second guard watches the actual EIEIO class definitions during ~load~, so macro-generated, conditional, and compiled definitions cannot bypass the layout check. Class-allocated slots and overrides that preserve the instance layout remain reloadable. If inheritance or the instance layout changed, the command stops before mutating that class and reports that Emacs must be restarted; redefining it would reinterpret live instance vectors and corrupt their state. If only the runtime guard could discover the unsafe definition, earlier non-class forms in the artifact may already have run, which is another reason to restart after that failure. Asynchronous build-and-reload records this outcome, and any other reload error, as a terminal failure instead of allowing an error to escape from the completion hook. By default, features that were already loaded are loaded again, and the main package feature is also loaded so locally rebuilt packages do not remain in an autoload-only state. With a prefix argument, all features provided by the package are loaded regardless of their previous state.

Identifying the classes a package previously defined means consulting ~load-history~, which holds an entry for every file the session has ever loaded. That list is scanned once per reload and matched on an extension-less absolute name, so reload time stays flat as a session ages; a file-system comparison is reserved for an entry whose base name matches one of the package's own files, which is what still lets a symbolic link under another name match. Comparing every entry against every file of the package through the file system instead made reload time grow with both counts, reaching roughly eleven seconds for an eleven-file package in a session holding thirteen hundred entries, during which Emacs was unresponsive.

** Update and reload
:PROPERTIES:
:CUSTOM_ID: h:update-and-reload
:END:

#+findex: elpaca-extras-update-and-reload
The command ~elpaca-extras-update-and-reload~ combines updating a package via Elpaca with an automatic reload. It prompts for a queued package, triggers ~elpaca-update~, and installs a temporary hook on ~elpaca-post-queue-hook~ to detect when the build finishes. If the build succeeds, it calls ~elpaca-extras-reload~ ([[#h:reload][Reload]]) and reports the result. If the build fails, it directs you to the =*elpaca-log*= buffer for details.

This provides a convenient single-step workflow: update, build, and force-load the new definitions.

The command returns a status token after enqueueing the build. Reloading is driven by ~elpaca-post-queue-hook~ when Elpaca's build process actually finishes. The completion callback isolates the reload from any active ~current-load-list~, so definitions cannot be attributed to an unrelated package whose load or build callback happened to be in progress. Callers that need a deterministic completion point should poll ~elpaca-extras-build-reload-status~ or ~elpaca-extras-format-build-reload-status~ for that token with short calls; they should not call ~elpaca-wait~ inside the daemon.

** Rebuild and reload
:PROPERTIES:
:CUSTOM_ID: h:rebuild-and-reload
:END:

#+findex: elpaca-extras-rebuild-and-reload
The command ~elpaca-extras-rebuild-and-reload~ is analogous to ~elpaca-extras-update-and-reload~ ([[#h:update-and-reload][Update and reload]]) but uses ~elpaca-rebuild~ instead of ~elpaca-update~. This is useful when you have made local source changes and want to rebuild the package from those changes rather than fetching upstream updates.

Build enqueueing and the later asynchronous autoload and compile steps use unbounded printing, so subprocess forms containing long dependency-path lists are serialized completely even when the live Emacs has customized ~print-length~ or ~print-level~.

** Lock file management
:PROPERTIES:
:CUSTOM_ID: h:lock-file
:END:

#+findex: elpaca-extras-write-lock-file-excluding
The command ~elpaca-extras-write-lock-file-excluding~ writes an Elpaca lock file to the specified PATH while filtering out packages listed in ~elpaca-extras-write-lock-file-excluded~ ([[#h:elpaca-extras-write-lock-file-excluded][User options]]). When called interactively, it prompts for the output file path.

The optional ELPACAS argument accepts a queue-like list as used by ~elpaca-write-lock-file~. When nil, the current queue is used. This makes it possible to call the function programmatically with a custom package set.
