* Overview

This directory contains the version-controlled parts of my Codex setup. The
shared Claude/Codex contract lives in [[file:../agents/README.org][the agent configuration overview]]; this
file covers Codex-specific activation, settings, and native differences.

├── config.toml        tracked native configuration
├── hooks.json         tracked hook registration

The live =~/.codex/AGENTS.md=, =~/.codex/config.toml=, and
=~/.codex/hooks.json= paths are symlinks to the tracked files. The installer
links =~/.codex/skills= to the tracked skill tree and exposes the programmatic
root used by =agent-run-skill=. Repo-root =.codex/= directories are
project-local and must never be used as global symlink targets.

The subtree owners are [[file:bin/README.org][the command index]], [[file:hooks/README.org][the hook index]], and
[[file:skills/README.org][the skill index]].

* Instructions

Codex reads user instructions from =AGENTS.md= in =$CODEX_HOME=. Project
instructions also live in =AGENTS.md= files, next to their Claude =CLAUDE.md=
peers. =project_doc_fallback_filenames= is deliberately absent: Codex does not
load project =CLAUDE.md= as a fallback.

The global =codex/AGENTS.md= and =claude/CLAUDE.md= files are semantic peers.
The audit normalizes tool-specific titles, paths, and Claude =@context= syntax
before comparison. User-facing replies use ASD-STE100 Simplified Technical
English.

Instruction files, skills, and hook reminders state current rules with their
reasons and without incident history, migration-relative wording, shouted
emphasis, or numeric output caps. The
[[file:../docs/superpowers/plans/2026-09-02-prompt-audit.md][2026-09-02 prompt-audit plan]] records the removed patterns.

* Native configuration

=config.toml= owns Codex model, reasoning effort, service tier, sandbox and
approval behavior, TUI preferences, trusted roots, plugins, MCP configuration,
and feature flags. =[features].hooks= enables the tracked hook integration.
Codex-only trust, plugin, theme, application, and MCP state does not need a
fictional Claude counterpart.

Hook trust belongs to an exact source path, handler key, and current definition.
Review the command identity when approving changed hooks; event labels alone
can name several handlers. Trust changes use Codex's configuration API and must
preserve unrelated settings and hook approvals.

The current default model is =gpt-6-astra=. Model, reasoning, and service-tier
choices are Codex preferences, not cross-tool parity requirements.

=bin/skill-prune= owns managed =[[skills.config]]= disable entries and keeps
them aligned with Claude's native skill overrides and
=skills-disabled.json=. Usage checks include default and active homes plus every
account home declared in =emacs/config.org=, deduplicate resolved account homes,
and refuse stale-skill decisions when evidence is unavailable or malformed.
=bin/codex-config-prune= removes stale project and hook
trust state. Generated or managed entries should be changed through their owner,
not edited as unexplained one-off configuration.

The =[projects."..."]= trust keys name absolute repository paths, so moving a
repository means rewriting its key. A running Codex appends its own trust entry
whenever it starts in a directory the config does not already cover, so a
rewrite has to merge with any entry Codex added for the new path rather than
land beside it. TOML rejects duplicate tables, and Codex reports a duplicate as
a fatal =failed to load configuration= that aborts every session, not as a
warning about the one affected project. The 2026-08-03 migration out of =~/My
Drive/repos= hit this: the rewritten =tangodb= key collided with an appended
one.

* Skills

[[file:skills/README.org][The Codex skill index]] documents discovery, programmatic and private roots,
managed =.system= content, pairing, and maintenance. The generated
[[file:../agents/skill-inventory.org][tracked skill inventory]] is the cross-tool catalog of repository-owned public
skills. Dynamic plugins, private skills, ignored runtime system skills, and
skills in other repositories are outside its scope.

The =profile-ai-cli-performance= skill measures selected client conditions
with exact terminal-success evidence and nullable, failure-aware paired metrics.
Dry runs do not access credentials or launch clients; selected conditions alone
determine dependencies. Unsafe token duplication and identity/provider changes
cannot be hidden as clean baselines. Private reports preserve incomplete cohorts
and unobserved isolation; timing completion does not establish a causal claim.

Browser control is runtime-owned: the bundled Browser and Chrome plugins load
directly through Codex. No tracked skill or helper command mediates a
CLI/Emacs-to-App browser handoff.

Model-invocable tracked skills do not preapprove bare high-risk tools through
=allowed-tools=. Loading a skill therefore leaves Bash, write, edit, agent, and
user-question permission decisions to the ordinary runtime policy. A narrowly
scoped Bash pattern may be declared when a skill genuinely needs one.

The paired =publish-dotfiles= skill reviews full history through bounded
commit-and-patch bundles. Merge commits are compared with every parent, and
scanner findings carry fingerprint-redacted source context, so fewer immutable
review records do not reduce the audited surface. Raw scanner reports are
confined to a private off-tree temporary workspace. Git scans use the same
zero-context patch stream as Gitleaks and never reinterpret patch coordinates as
blob lines; directory scans use authoritative source lines and advisory
byte-column spans. Schema-4 runs separate scrub values from keyed review
signatures. Review writes are locked so bounded agent pools cannot overwrite one
another's verdicts.

Readiness uses an enforced non-publishing scan mode that preserves refs and
=FETCH_HEAD=. Full-audit receipts age from the scan and cannot clear later
incident invalidations; missing advertised public objects fail the audit closed.
Release authorization binds the exact tag name reviewed by the scan. Read-only
checks never authorize history repair or provider-side credential changes.
Audit receipts bind the reviewed scan and manifest, including across concurrent
same-boundary rescans; earlier clean status cannot certify a replacement.

The paired =release-dotfiles= skill preserves the profile-test gate, excludes the
read-only Elpaca mirror from package pushes, and verifies live recipes before
serializing a lockfile. It uses supported GitHub PR fields, strict release tags,
path-only version commits, and the same approved notes file for review and
release creation. Preparation alone grants no publication authority.

The paired =proofread= skill resolves one external Node dependency runtime for
both setup and execution, canonicalizing both its root and actual =node_modules=
destination before rejecting paths into this Drive-synced tree. Only the LLM
engine consumes an injected provider key; skill-local plaintext =.env= files
are no longer loaded. Review-only work does not write copies or imply provider
transfer. Editing preserves source files, requires validated literal changes,
and distinguishes engine failures and protected-syntax gaps from clean results.

The paired =move-session-log= skill rewrites session metadata and Codex's
project-filtered thread index using exact session identities and known metadata
fields, preserving historical tool records. It inventories discovered shared
profiles' active/archive stores, history, indexes and databases; absent artifacts
and discovery limits are explicit. Dry-run reads captured SQLite snapshots,
including WAL state, without opening originals for recovery. Apply requires
offline stores, writer checks and private recovery backups. Per-file and SQLite
operations are not one transaction; a journal records partial failures. Metadata
readback is distinct from observing the actual live resume consumer. Database
updates cover thread =cwd=, not independent project associations; unsupported
generations and schema side effects refuse before writes.

The paired =orchestrate-review= skill coordinates fixed Claude and Codex
sessions through one guarded, stage-atomic workflow. Its helper binds each
actor's backend, repository, and transcript, and records delivery attempts
before contact. Unique user-message receipts distinguish delivery from
background transcript growth; terminal assistant returns distinguish completion
from tool activity. Ambiguous restarts and steering require reconciliation,
not another submission. Shared session primitives live in
=lib/python/agent_session_lib.py=. During implementation, monitoring exposes
the fixed actor's state and its published progress, not internal task
transcripts or processes. The watcher does not automatically enforce a timed
stop-loss or detect login screens. Agents use supported host waiting mechanisms
and keep the host's required update cadence. Cleanup closes only run-owned,
confirmed-inactive sessions; adopted or busy sessions remain protected.

The paired =request-review= skill runs one cross-model review of a
committed plan from inside the authoring session: it anchors the review to
the exact committed blob (the reviewer reads =git show <commit>:<path>=,
never the working tree), enforces an opposite-backend fresh-reviewer identity
invariant at initialization (verified against the buffer's detected backend,
not just the declared label), permits exactly one marker-gated review pass
(markerless returns are terminal) and one zero-output process-loss restart,
and leaves adjudication and implementation in the current session. Once
=finish-review= has recorded the return, the reviewer session is killed;
the run file and transcript path are the inspection record. Because a
fresh Codex session materializes its rollout transcript only on first
delivery, the helper rebinds to the discovered transcript once it provably
contains the run's marker-bearing prompt. Its helper reuses the same shared
=agent_session_lib= module.

Delivery and manual reconciliation require the prompt's marker in a new user
message after the saved transcript boundary. Busy state and unrelated transcript
growth do not acknowledge delivery. Emacs client calls time out after 15 seconds;
an ambiguous result leaves the submission pending for receipt reconciliation.

* Hooks and rules

The tracked =hooks.json= is the registration source. It lives outside the
dotfiles repo's project-local =.codex/= directory so Codex does not load it
twice. Registrations normalize Codex payload and tool-name differences before
dispatching to the paired scripts documented in [[file:hooks/README.org][the hook index]].

Sensitive-read guards permit the security audit's shell-export classifier only
for its exact absolute helper and target paths. The classifier reports names,
line numbers, scopes, and classifications without printing values.

The GitHub write guard requires committed repository authorization for every
push and mutating =gh= operation, including topic branches, pull requests,
issues, and comments. It classifies each literal shell command nested in
=functions.exec= independently and refuses dynamic or ambiguous nested calls;
read-only GitHub inspection remains available for undeclared repositories. A
registry match falls through silently rather than explicitly approving the
write, including for pull-request merges, so the normal permission layer and
the global user-authorization rule still apply.
The Elisp post-edit hook is registered on the outer composed-tool event as well
as direct edit events, so it recovers changed paths from nested patches instead
of depending on the nested runtime to dispatch a separate pre-tool event.

Security guards block unexpected runtime and bootstrap failures with exit code
2. Secret scans include native =Write.content= and =Edit.new_string= as well
as patch text; the [[file:hooks/README.org][hook contracts]] list the covered entry points.
The regression fixtures exercise those actual entry points with malformed
input, missing dependencies and startup helpers, and harmless editing payloads.
These guards run with the agent's OS user and filesystem access.

The secret guard denies direct agent-shell invocations of raw =op=, =pass=,
macOS =security=, and =pbpaste=, including wrappers, nested shells, process
substitution, executable globs, and shell-word obfuscation. The 1Password
brokers =op-automations= and =op-desktop= are the sanctioned access path:
=lib-op-policy.py= allows a closed list of command shapes whose stdout carries
no credential (masked =run=, captured or filed =read=, metadata-only =jq= over
item output, =--out-file= documents, writes without =--format=, metadata
commands) and denies every other shape, including shapes it cannot place and
a broker named outside a literal nested exec command. Shell expansions are
fine in broker arguments; an expansion in the subcommand position is
unclassifiable and denied. Quoted
argument globs, including =rg= exclusion patterns beginning with =!=, remain
inert data rather than executable command words. A shell =case= default pattern
is likewise grammar, not an executable glob. Heredoc bodies fed to a known data sink (=cat=, =tee=, =git=, =gh=, and
similar) with no pipe or substitution around them are data too, so a commit
message or a Markdown file written through a heredoc is never scanned as
shell text; bodies fed to shells, interpreters, or unknown programs stay in
the scan. For a narrowly recognized quoted Python stdin program, the secret
guard first checks Python protected references, exempting only genuine =pass=
statements, then excludes that body from shell lexical checks. Python varargs
are not shell executable globs. Other secret checks still receive the original
input; unknown source stays unmasked and safe protected-name string mentions
remain conservatively denied. This classifier is not a Python sandbox.
Nested shell commands are decoded with valid UTF-16 surrogate pairs preserved.
The secret guard validates all extracted command contexts before classifying
any of them; malformed contexts, unsupported NULs and extraction failures deny
execution rather than turning a failed extraction into an empty command list.
The sensitive-read guard applies the data-sink rule and names the
heredoc in its denial when a path is mentioned only inside an
interpreter-fed program. A shell =eval= is recognized only at a word
boundary, so an =emacsclient --eval= argument is Elisp, not shell.

The Elisp post-edit hook rebuilds and reloads complete package worktrees, but
skips test-only files and edits while Git has an active operation or unmerged
index entries, so a live Emacs never loads tests or a partially resolved tree.
The batch runner loads canonical source and emits evidence bound to the
repository, package, and source revision; commit guards reject stale or reused
evidence.  Composed-tool responses arrive as arrays of text blocks; the hook
payload normalizer joins those blocks before evidence tracking, so successful
=functions.exec= checks create the same session marker as direct shell checks.
Test-only Elisp commits likewise do not require package-manual
updates. For =functions.exec= wrappers, post-commit verification pairs each
literal nested shell command with its own =workdir=; it never guesses from the
hook process directory and ignores inert quoted commit text. It records every
production package across multi-commit commands. Only =elisp-live-verify= can
clear one matching repository/package/commit obligation. The helper rejects
dirty source, waits for the package reload, and then runs the package-named live
expression. Unrelated =emacsclient= calls do not clear the gate.

Emacs-owned sessions use eight explicit =codex-hook-wrapper= registrations for
lifecycle forwarding. The wrapper comes from the Emacs package source tree
because the build tree does not contain that script; its configured source path
and Emacs socket are part of the integration. Shell matchers cover the supported
shell and execution tool names; edit-style tools share compact matcher groups
that must remain consistent with the trusted-tool list. =UserPromptSubmit= uses
the event's required empty matcher. Stop and compact events forward lifecycle
state; they do not create a Claude Notification event.

=rules/default.rules= is the native command policy. Hook allow/deny decisions
supplement it; allowing one layer does not bypass another guard or authorize an
external write.

Hooks that judge a Git command resolve the repository from the command itself,
via =hooks/lib-repo-root.sh=. A =cd= at any command head decides the repository,
the last one winning, because a session working in one repository routinely
commits in another and the =cd= is often preceded by a preamble. The target is
extracted by parameter expansion, never evaluated; =$HOME= is substituted, and a
target carrying command substitution or any other unexpanded variable is treated
as unresolvable. When the target cannot be resolved the helper reports no
repository at all rather than substituting the session's own, since judging a
tree the command never touched both refuses correct commits and approves ones it
should refuse. Nested Bash events from =functions.exec= omit their literal
=workdir= and report the session directory instead. For those events, the Codex
helper matches the exact command to the most recent parent =tools.exec_command=
record in the session transcript and accepts only one unambiguous, existing
workdir. The Elisp evidence gate recovers this context before routing the
command, while the original transcript metadata is still available.

Commit guards check explicit path selections against a disposable candidate
index, leaving unrelated staging untouched. An =--only= directory selection
includes tracked files and staged additions even below ignored directories, but
excludes untracked siblings. Untracked documentation cannot satisfy a requirement
for a commit that would omit it. Inspection rejects configured clean filters
without executing them. Unsupported selection syntax is denied with a reason
rather than checked against a different candidate.
Quoted commit-message heredoc delimiters, like their bodies, are shell input
rather than Git path selections. Interpreter-fed heredocs remain visible to
the command classifier.

Guards that inspect a Git command read its arguments only, never its message.
Heredoc bodies are dropped before lexing, because an apostrophe in prose made
the lexer raise and the parser fail closed on a commit that staged no Elisp at
all; argument text that genuinely cannot be lexed still fails closed. Since
these hooks run before the =git add= they are judging, the paths a command is
about to stage count as staged. A second =git commit= in the same
command is modelled in sequence when =&&= links it to the first: the adds
between the two commits are its content, and the guard audits the union,
which is the tree the whole command leaves behind.

* Verification

After changing shared configuration, run =bin/ai-config-sync audit=. After a
tracked public skill name or catalog description changes, run
=bin/docs-audit generate= first. For hook changes, verify the registration in
=hooks.json= and exercise the real Codex event payload as well as the standalone
script.

Codex's instruction discovery, tracked native configuration, lifecycle hooks,
rules, plugin state, and managed system skills are genuine differences. They
remain explicit rather than being hidden by fallback behavior.
