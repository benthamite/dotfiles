#+title: Emacs freeze incidents

Running record of Emacs freezes and slowdowns: what each investigation found,
what was changed, and what is still open. The =emacs-freeze= skill reads this
before diagnosing, so that a session does not re-propose a remedy already
tried. Append one entry per investigation; update the open items and
the "Already tried" list in place.

* Evidence sources

- Watchdog: =bin/emacs-server-watchdog=, run each minute by launchd.
  - Outage/recovery log: =~/Library/Logs/emacs-server-watchdog.log= (local
    time).
  - Per-minute samples: =~/Library/Logs/emacs-server-watchdog.samples.jsonl=.
    Fields include probe result and failure kind, state-file age, GC count and
    seconds since the previous sample, Emacs footprint, swap, top processes.
    =time= is epoch seconds; convert with jq =strflocaltime=, not =strftime=
    (UTC).
- State file =~/.cache/emacs-server-state.json=, written every 5 s by
  =simple-extras-server-state-mode=. Stale means timers are not running.
- Display sleep/wake: =pmset -g log=. Several outages ended seconds after the
  display woke, i.e. Emacs froze while Pablo was away.
- Stacks: since 2026-10-10 the watchdog runs =/usr/bin/sample= when a probe
  fails or a minute has 30+ GCs (at most every 5 min) into
  =~/Library/Logs/emacs-server-watchdog.stacks/=; the sample line's
  =stack_file= names the report. It finishes 20-80 s after the run.
  Native-compiled Lisp shows as =F<hex>_<name>_N= symbols.

  is not a fix: the memory refills within ~20 min of every start (see the

  briefly while the code that feeds it stays loaded.

** 2026-10-25 21:33–22:19: main-thread DNS from forge timers and NSM (remedies proposed)

- Pablo: unresponsive again. Watchdog: timeout 21:33:50 (recovered 21:34:54),
  refused 21:39:39 (recovered 21:41:06), stacks at 20:52, 21:32 and 22:18.
  Server answered again by ~22:20.
- Network: Mullvad is now the default route (=utun5=), DNS via its local
  resolver 127.88.19.60; Tailscale also connected. =slack.com= resolved in
  0.7 s at 22:19. Whether Mullvad was turned on deliberately: unknown.
- 22:18 stack: timer =tlon-pull-issues-in-all-repos= → =forge--query= →
  =ghub--retrieve= → =url-retrieve= → =open-gnutls-stream= → =getaddrinfo= →
  =kevent= (68 of 82 main-thread samples).
- 22:19 sample (=/tmp/emacs-freeze.jmC5jC/s1.txt=): a nowait TLS connection
  finished inside =wait_reading_process_output= (caller unknown) →
  =finish_after_tls_connection= → =nsm-verify-connection= →
  =nsm-check-tls-connection= → =nsm-should-check= →
  =network-lookup-address-info= → =getaddrinfo= (2538 of 2584 samples).
  In Emacs 30.2 =nsm-should-check= resolves the host unconditionally, but the
  result is only used when =nsm-trust-local-network= is non-nil; live value
  is nil, so the lookup is pure cost.
- 20:52 and 21:32 stacks contain Slack websocket and =request= frames; where
  they blocked was not established.
- Live network timers (22:20): =tlon-pull-issues-in-all-repos=,
  =epoch-pull-forge-repos=, =forge-extras-pull-notifications=,
  =doom-modeline--github-fetch-notifications=, =elfeed-extras-update=, plus
  local or subprocess ones (activity-watch, copilot, =tlon-repos-pull-babel-refs=).
- Proposed remedies (pending Pablo's approval):
  1. =el-patch= =nsm-should-check= in config.org so it calls
     =network-lookup-address-info= only when =nsm-trust-local-network= is
     non-nil.
  2. One shared helper that, before each run of the network timers above,
     resolves/reaches the target host in an async =curl= subprocess
     (=--max-time 5=) and skips the run on failure; name it in the
     =elisp-conventions= network rule. Narrows, does not close, the window:
     DNS can degrade between the probe and Emacs's own lookup, and a network
     change may flush the system resolver cache.
  3. The same probe before Slack's websocket reconnect.
  4. Deferred: report the =nsm-should-check= lookup upstream (email to the
     Emacs bug tracker under Pablo's name).

** 2026-10-25 13:04–20:44: Slack websocket TLS handshake with no timeout (fixed in dotfiles =a9624ab02=)

- Pablo: froze while the internet was down. Watchdog: timeouts from 13:04,
  refused from 14:22, state file stale throughout, recovered 20:44:37.
- All 19 watchdog stacks, 13:04 to 16:31, show the same main-thread path:
  =request= callback → =slack-ws-reconnect-with-reconnect-url= →
  =websocket-open= → =open-network-stream= (TLS) → =gnutls-boot= →
  =gnutls_try_handshake= → =nanosleep=. In Emacs 30.2 that function retries
  a blocking client's handshake every 10 ms until it succeeds or hits a fatal
  error. Only C-g (=maybe_quit=) can stop it, since timers do not run.
  A connection whose peer goes silent blocks Emacs until the socket fails.
- Why blocking: emacs-slack's =websocket-nowait= slot defaults to nil, and
  =slack-extras-teams= does not set it. With nil, slack's 20 s connect-timeout
  timer is armed but cannot fire while the handshake blocks.
- 20:43 sample, after the handshake ended: a timer running =org-roam-db-sync=
  (via =simple-extras-call-verbosely-in-background=) after the 7.5 h stall;
  the server answered a minute later. What ended the handshake is unknown.
- Same class as the morning's DNS stalls: a network wait on the main thread
  with no deadline.
- Fix: =:websocket-nowait t= alone did not help. websocket.el's
  =websocket-ensure-handshake= sends the handshake while a nowait connection
  is still connecting, which blocks in =wait_while_connecting= the same way
  (reproduced live at 20:48 against a silent local server; that test froze
  Emacs for ~20 s). Upstream =main= has the same code. Now patched with
  =el-patch= in config.org to send only once the connection is open, and both
  teams set =:websocket-nowait t=, so slack's 20 s connect timeout can fire.
  Batch test against a silent server: Emacs ran 16 event-loop turns in 8 s
  (unpatched: blocked 14 s); a real echo server still connected. Live: a
  Forethought reconnect returned in 4 ms and connected within 4 s. Not tested
  with the network actually down. Upstream PR not prepared yet.

** 2026-10-25 10:33–11:09 and 12:08–12:11: synchronous DNS in the usage poller (fixed in agent =74e859b=)

- Not host load: load ~8, Emacs 1999 at 4% CPU, recursion depth 0.
- All five watchdog stacks from 10:37 to 12:09 have the main thread
  (100% of its samples) in =getaddrinfo= → =mdns_addrinfo= → =kevent=,
  reached from =url-retrieve= → =open-gnutls-stream= →
  =make-network-process=, called from a timer through bytecode (10:37, 11:05),
  and from =url-http-end-of-document-sentinel= at 12:04.
- Most likely caller: =agent-usage--poll= (bytecode, every 300 s), which calls
  =url-retrieve= for 9 accounts (4 Claude at =api.anthropic.com=, 5 Codex at
  =chatgpt.com=). Not proven: the bytecode frames hide the function.
  On macOS Emacs resolves names synchronously on the main thread even with
  =:nowait=, so each lookup blocks Emacs.
- Why lookups are slow: Wi-Fi DNS is set by hand to 1.1.1.1/1.0.0.1, and
  the current network (gateway 10.254.221.206) blocks DNS to 1.1.1.1 (UDP
  and TCP time out; ping works). Tailscale MagicDNS (100.100.100.100) took
  0.3–1.2 s per query, =getaddrinfo= 0.5–3.9 s. The network's own resolver
  (DHCP, 10.254.221.206) answered in 8–12 ms.
- Fix: agent =74e859b= fetches usage through =agent-usage-http-get=, a =curl=
  subprocess with a 30 s cap and token headers on stdin. ERT covers a silent
  server (Emacs keeps running); live fetches for both backends succeeded.
  Rule added to the =elisp-conventions= skill: no network waits on the main
  thread from timers, sentinels, filters or hooks.
- Samples: =/tmp/emacs-freeze.RD0CI2/=.

** 2026-10-12 23:19 → 10-13: agent.el status-query loop (fixed in agent =5bb959a=)

- Server unanswered from 23:19, refused from 00:47 (listen backlog full);
  Emacs 24375 at 100% CPU throughout. Not memory: swap 17 GB, load ~11.
- 08:49 stacks: ~500+ nested =kill-buffer= → =delete-process= →
  =status_notify= → sentinel → =kill-buffer= frames (sampler truncates the
  root), with =claude-code--find-all-claude-buffers= and
  =generate-new-buffer-name= as leaf work. Emacs spawns a =claude= child
  about once a second; open pipes swing between ~340 and ~1300.
- Source: =agent-claude--query-agents-status= / =--finish-agents-query=
  (agent.el =2af0543=, 2026-10-11). The sentinel kills the query's buffers,
  and that runs other exited queries' sentinels inside it; it also starts the
  rerun query from inside the sentinel. Inferred: a self-feeding nesting loop.
- 00:53 stacks: a timer's =make-process= (the scheduled query) signalled a
  file error, =debug-on-error= opened a debugger, and timers inside it
  repeated the failure. =get-process= scanned a huge process list and
  =generate-new-buffer-name= a huge buffer list, so query buffers and
  processes were leaking. The exact errno was not captured; fd exhaustion
  is a guess.
- Recovery: SIGUSR2 at 09:54 unwound the chain into nested debuggers
  (timer =make-process= failing to create a pipe), but the server stayed
  unanswered and the loop resumed within 4 min. SIGTERM was approved;
  the agent's permission classifier blocked it, so it was handed to Pablo.
- Fix: agent.el finishes queries from a timer, never inside the sentinel;
  an exited but unstored query blocks duplicates; a query that cannot start
  becomes an error result (3 regression tests fail before, pass after).
  Committed and pushed as agent =5bb959a= on 2026-10-13 by a later
  session, the diagnosing one having ended with the frozen Emacs. Checked
  live: a query that cannot start stores an error and leaks no buffer.
  The nesting loop itself was not reproduced live.
- The 10-11/10-12 outages started the day this code landed; the earlier
  ones (10-06 to 10-10) predate it and have other causes.
