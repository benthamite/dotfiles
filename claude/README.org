#+title: Claude Code configuration
#+author: Pablo Stafforini

* Overview

This directory contains the tracked parts of my Claude Code setup. The shared
Claude/Codex contract lives in [[file:../agents/README.org][the agent configuration overview]]; this file covers
Claude-specific layout, activation, and settings.

* Layout and activation

#+begin_example
claude/
├── CLAUDE.md          global instructions
├── bin/               service and maintenance commands
├── context/           reference material loaded when needed
├── hooks/             hook implementations
├── skills/            tracked public global skills
├── private-skills/    encrypted skills exposed through local shims
└── README.org
#+end_example

The live =~/.claude/CLAUDE.md= and =~/.claude/skills= paths are symlinks to the
tracked instruction file and skill tree. By contrast,
=~/.claude/settings.json= is a mutable regular file: Claude rewrites it when
settings, permissions, hooks, or plugins change, so a symlink would be unsafe.
=~/.claude/settings.local.json= holds machine-local permissions and native
skill-disable state.

The shared live settings set =disableClaudeAiConnectors= to =true=. Claude Code
therefore does not load hosted claude.ai connectors or their tool schemas.
Service access uses the canonical local CLIs and scripts documented in
=CLAUDE.md= instead.

Per-project configuration belongs in =<project>/.claude/=. Repo-root
=.claude/= directories are project-local and are never global symlink targets.
Account-specific homes selected with =CLAUDE_CONFIG_DIR= isolate authentication,
projects, history, plugins, and settings while continuing to use deliberately
shared tracked artifacts.

** Multi-account activation

Four OAuth accounts use separate configuration homes:
=~/.claude-personal/=, =~/.claude-tlon/=, =~/.claude-epoch/=, and
=~/.claude-trajectory/=. Each keeps its own OAuth identity, Keychain credentials,
and =.claude.json=. Settings, skills, projects, history, and plugins are shared
through symlinks to =~/.claude/=. The account homes do not contain a second
=CLAUDE.md=, because the user-level file is already loaded from =~/.claude/=.

The selected account is stored in =~/.claude-current-account=. Emacs reads that
selection through =agent-claude-start-or-switch= and changes it with
=agent-claude-select-account=; terminal aliases select the same four account
homes. Before launching a newly configured account, run
=agent-claude-init-account= so its shared paths are symlinks from the start.
Otherwise Claude may create divergent regular settings and history files on
first login. The initializer heals untouched files but leaves non-virgin files
for explicit migration.

The =claude= PATH shim removes ambient =ANTHROPIC_API_KEY= and
=ANTHROPIC_AUTH_TOKEN= because they take precedence over the selected OAuth
account. =CLAUDE_CODE_ALLOW_API_KEY_AUTH=1= is reserved for a deliberate
API-key-authenticated Claude session.

* Instructions and settings

=claude/CLAUDE.md= is the user-level instruction source. A project may add a
sibling =CLAUDE.md= and project-local settings. User and project settings are
additive. Account selection changes which user-level native state is active; it
does not introduce a third precedence layer. Effective behavior therefore
depends on both tracked instructions and the selected live state.

Operating rules in =CLAUDE.md= stay short and state the behavior directly. The
file is a lean always-loaded instruction source, not a manual: detail belongs in
skills and context files that load on demand. User-facing replies lead with the
answer and stay plain and brief: short sentences, no preamble, and nothing that
does not change what the user does or decides.

The global instructions state the repository-root contract shared with the
Codex side: every repository lives outside Drive under =~/repos/= (Epoch
repositories under =~/repos/epoch/=), nothing under the Drive sync root may
hold dependencies, builds, caches, virtual environments, or worktrees, and
every linked worktree lives under =~/repos/.worktrees/<repo>/<name>=. The
108 repositories that used to sit under =~/My Drive/repos/= were moved on
2026-08-03; =regenerate-coverage-map.sh= and the other hooks that name a
repository path were updated in the same change.

The live global settings register hooks by absolute path. Stop forwarding to
Emacs is a turn-end signal, not proof that the agent process exited. Reusable
lesson capture belongs to the Emacs =agent-before-exit= flow and must not be
silently reintroduced as a Stop hook. The permission mode is automatic: guards
return allow or deny and never prompt as an approval mechanism.

Claude-specific browser, OAuth, hosted connector, and account state stay in
Claude's native stores. Shared MCP wiring is audited only when it is declared in
=ai-config-sync.json=; placement and account guidance lives in
[[file:context/mcp-servers.md][the MCP reference]].

* Skills

[[file:skills/README.org][The Claude skill index]] documents discovery, pairing, private and programmatic
roots, and maintenance. The generated
[[file:../agents/skill-inventory.org][tracked skill inventory]] is the repository-wide catalog. It covers tracked
public skills only; runtime plugins, private skills, ignored system content,
and skills owned by other repositories are outside its scope.

The =profile-ai-cli-performance= skill benchmarks clean and configured Claude
Code and Codex processes with pinned per-client settings, preflight checks, and
comparable latency metrics. Its =--only= flag restricts the run to named
conditions, which keeps the Claude clean-versus-configured comparison available
when the other client fails preflight on quota or authentication. The isolation
checks then apply to the selected conditions only, and the cross-client
comparison stays unavailable.

Browser control is runtime-owned rather than mirrored through a tracked
Codex-App handoff skill. Claude therefore carries no pointer skill or helper
command for moving a Codex thread into the desktop app.

The paired =proofread= skill resolves one external Node dependency runtime for
both setup and execution, canonicalizing both its root and actual =node_modules=
destination before rejecting paths into this Drive-synced tree. Its package
commands continue to read the skill-local scripts and =.env= file.

The paired =personalize= skill carries a hard concision rule: outgoing drafts
carry only what the recipient needs to act or decide, lead with the ask, and
hold Slack replies to a few sentences.

The paired =humanize= skill owns the single tells catalogue that =personalize=
reads by reference. Beyond the Wikipedia-derived tells it launched with, the
catalogue covers the engagement register (throat-clearing openers, faux-insight
setups, colon reveals, fake-profound kickers, and kin) merged from
petergyang/no-ai-slop.

Org task triage is split across two skills over one engine. =triage-personal-todos=
here owns personal notes; the project-local =triage-project-todos= in the Epoch
workspace owns Epoch work. They share the engine, the task fingerprints, the
snapshot binding and the transactional write, and differ only in which corpus
they cover and which nine-row priority table the model judges against. The split
exists because that table is the thing that differs, and choosing the wrong one
fails silently: it writes a priority cookie with provenance attached, which the
other skill then reads as settled. Each inventory and prepared manifest records
its corpus, and verification reads it back out, so a run prepared against one
corpus cannot be verified or applied as the other. =bin/triage-notes= is the only
place that knows where the shared engine lives.

Both skills offer the same =a/s/d/r/m= shortcuts on a briefed task: action it,
skip it for the session, close it as already done, reprioritize it, or record it
as non-actionable. =d= exists because a stale record is a common outcome rather
than an edge case, and because the engine cannot express completion — so =d= is
a direct Org edit rather than a prepared update. It verifies from the source
rather than the heading, flips to =DONE= with =CLOSED= and =LAST_VERIFIED=,
records the check that settled it, and splits out anything the closure leaves
open. Partial completion is a rewrite, not a close.

Both also check the selected task against its live source *before* briefing it,
and check that its premise still holds — a separate failure that no date can
catch, where every fact in the entry is still true but the question has stopped
being a question because the design or situation moved underneath it. The Epoch
skill gained these on 2026-08-13 after one run briefed five dead tasks; the
personal skill gained them on 2026-08-14, since the failure is not
Epoch-specific and the gap between a personal note and the world is usually
wider. What the checks find lands in the existing reason codes, which for
personal notes are most often =stale= or =already-complete=.

The paired =update-log= skill runs its post-update-log hooks *before* it writes
the =CLAUDE.md= pointer, because the project brief those hooks refresh is what
the map summarises; the reverse order digests the state the project was in
before the session. The step order encodes that dependency rather than
describing it. Until 2026-08-13 the pointer step came first while instructing
the reader to work from a brief the hooks had not refreshed yet, so in practice
the digest came from the session log.

Two writing rules follow from the same defect. =Current focus= selects from the
brief's open tasks deterministically — priority order, non-actionable keywords
skipped unless everything is blocked, each task carried by its own heading text
rather than paraphrased, defined empty state — so two runs over one brief agree.
And no derived field may *originate* a claim that work is outstanding, pending,
blocked, or awaiting somebody: those fields carry neither evidence nor a date,
so such a claim belongs on the task holding =VERIFY_WITH= and =LAST_VERIFIED=.
A derived field may repeat it; it must not be where it first appears. Epoch's
=NEXT_STEP= and =STATUS_DETAIL= take the same rule through
=projects/context/project-doc-conventions.md=.

The =move-session-log= skill bundles a Python adapter
(=skills/move-session-log/scripts/move_session_log.py=) that mirrors the Codex
adapter's interface — single-session import plus =--dry-run=/=--rename OLD
NEW= — with byte-equivalent path-mapping semantics, so the Drive workspace
migration tooling can relocate session history for either tool. Its JSONL
rewrites resolve symlinks before writing, so a profile that shares its
=history.jsonl= via symlink (e.g. =~/.claude-epoch= → =~/.claude=) keeps the
link intact instead of getting a diverged copy.

The paired =orchestrate-review= skill coordinates fixed Claude and Codex
sessions through one guarded, stage-atomic workflow. Its helper recognizes the
canonical =claude-code= and =codex= backends, uses Codex's public prompt reader
for app-server delivery recovery, and can rebind a failed author or reviewer
phase to a fresh transcript without enumerating unrelated sessions. The
single-actor session primitives it relies on — guarded prompt delivery,
transcript-boundary acknowledgment, marker-gated transcript reads, and buffer
lifecycle inspection — live in the shared =lib/python/agent_session_lib.py=
module, which its helper loads by resolved file path. Stage sessions are
disposable: the skill requires killing both fixed actor sessions (and any
priming session) as soon as a run reaches a terminal state, so no finished or
unused agent buffers linger. The injected implementation contract also forbids
Agent 1 from ending its turn to wait on background jobs or subagents; it must
poll inside the turn with bounded loops.

The paired =request-review= skill runs one cross-model review of a
committed plan from inside the authoring session: it anchors the review to
the exact committed blob (the reviewer reads =git show <commit>:<path>=,
never the working tree), enforces an opposite-backend fresh-reviewer identity
invariant at initialization (verified against the buffer's detected backend,
not just the declared label), permits exactly one marker-gated review pass
(markerless returns are terminal) and one zero-output process-loss restart,
and leaves adjudication and implementation in the current session. Because a
fresh Codex session materializes its rollout transcript only on first
delivery, the helper rebinds to the discovered transcript once it provably
contains the run's marker-bearing prompt. Its helper reuses the same shared
=agent_session_lib= module.

The =fix-drive-errors= skill treats the fully paginated native Drive panel as
the source of truth. Its helper preserves duplicate rows and exact error
reasons, inventories all candidate paths without claiming a basename match is
the offending instance, and fails closed when accessibility traversal is
incomplete. The skill also covers rejected cross-account =.gdoc= pointers and
routes their replacement through ordinary =epoch-doc:= URL shortcuts rather
than sharing changes or another Drive-hosted symlink.

* Hooks

[[file:hooks/README.org][The Claude hook index]] owns registration boundaries and the per-file index.
Claude has events with no Codex equivalent here, including =Read=, =Grep=,
=Glob=, =Skill=, Notification, and Chrome-specific events. Those are explicit
manifest differences, not missing peers.

Sensitive-read guards permit the security audit's shell-export classifier only
for its exact absolute helper and target paths. The classifier reports names,
line numbers, scopes, and classifications without printing values.

Their auth-aware allowlist admits the =op-automations= and =op-desktop= brokers
alongside raw =op=. The secret-leak guard requires those brokers in place of raw
=op=, so recognizing only the raw form left commands that also name a
credential-bearing path with no permitted invocation at all.

The Elisp post-edit hook rebuilds and reloads complete package worktrees, but
skips test-only files and edits while Git has an active operation or unmerged
index entries, so a live Emacs never loads tests or a partially resolved tree.
Test-only Elisp commits likewise do not require package-manual updates.

Live-verification evidence for a standalone-package label binds to the
package's own checkout, resolved through =bin/elpaca-package-path=, never to
the shell's working directory. The verify-after-commit gate keys its debt to
the committing repository while blocking =cd=, so a harness that pins the
working directory to the dotfiles root could otherwise never clear a debt for
a commit in a package repository.

Hooks that judge a Git command resolve the repository from the command itself,
via =hooks/lib-repo-root.sh=. A =cd= at any command head decides the repository,
the last one winning, because a session working in one repository routinely
commits in another and the =cd= is often preceded by a preamble. The target is
extracted by parameter expansion, never evaluated; =$HOME= is substituted, and a
target carrying command substitution or any other unexpanded variable is treated
as unresolvable. When the target cannot be resolved the helper reports no
repository at all rather than substituting the session's own, since judging a
tree the command never touched both refuses correct commits and approves ones it
should refuse.

The GitHub write guard resolves the target repository from the command before
it falls back to the surrounding checkout's remote. =gh repo= verbs name their
target positionally and =gh api= endpoints are read through a leading slash or
surrounding quotes; both used to miss, leaving the ambient repository to stand
in, so an unowned target inherited whatever allowlist entry that repository
had. =gh repo create= now refuses a command that names no =OWNER/REPO= at all,
because a creation never acts on the current repository and so cannot borrow
its authorization.

Every GitHub write now requires committed repository authorization. Topic
branches, pull requests, issues, and comments have no contribution exemption;
read-only inspection remains available for undeclared repositories. The
allowlist, guard implementation, and hook registrations remain agent-editable;
there is no separate self-edit guard.

A change under =claude/skills=, =claude/hooks=, =claude/settings*.json= or
=claude/CLAUDE.md= must be accompanied by an update to this file. The guard
accepts only that exact path, named among a command's =git add= arguments: some
other README does not stand in for it, and a commit message mentioning the file
is not an update to it. Both were previously accepted, which is how the triage
split reached this repository undocumented.

Guards that inspect a Git command read its arguments only, never its message.
Heredoc bodies are dropped before lexing, because an apostrophe in prose made
the lexer raise and the parser fail closed on a commit that staged no Elisp at
all; argument text that genuinely cannot be lexed still fails closed. Since
these are =PreToolUse= hooks they run before the =git add= they are judging, so
the paths a command is about to stage count as staged.

The SessionStart reasoning-worktree synchronization hook is also Claude-only.
It repairs required key links before eligibility checks, updates eligible
worktrees without pushing, reapplies the local overlay, injects private
project skills, and installs worktree-local freshness protection. Because the
key repair precedes the eligibility checks, it delays the start of every
session in every repository, and it therefore starts no subprocess while the
links are correct. Keep it that way: an added =basename= or =readlink= for each
worktree previously cost approximately 0.41 seconds of session start time. Its bulk
wrapper fetches shared state once before processing multiple worktrees. All
worktree-creating helpers construct destinations under the shared external
root =~/repos/.worktrees/<repository>/<branch>= — never inside a repository
checkout or =~/My Drive= — while maintenance helpers keep covering legacy
worktree locations until those are migrated.

* Verification

Run =bin/ai-config-sync audit= after changing shared configuration. When a
tracked public skill name or catalog description changes, first run
=bin/docs-audit generate=. For a registered hook change, verify both its
standalone decision logic and the real Claude event path; mutable
=~/.claude/settings.json= registration is part of that behavior.

Claude's settings format, event surface, permission model, browser integration,
and account overlays are genuine tool-specific state. The sync contract records
those differences rather than forcing them into Codex-shaped files.
