# Alerting for Pablo's automations

When an automation must run on time, the same service also triggers it: see `scheduling.md` (2026-11-02).

Principle (2026-10-09): liveness and failure alerts for Pablo's automations go through one service, `launchd-heartbeat`, applied the same way in every project. Do not build a project's own watchdog Worker, push topic or alert channel; extend the shared service instead.

GitHub notifications (Pablo, 2026-10-23; applies in every project: personal, Epoch, Forethought): a GitHub Actions run whose failures an alerting service covers (this service, Epoch's or ph-ps's watchdog) must not generate a GitHub notification at all. GitHub notifies whoever a run is attributed to (the pusher, the dispatcher, the last editor of a `cron:` line), so such runs are started by an App or bot identity, never by Pablo: dispatched through the App, push checks started by an App dispatcher, cron lines last changed by the App. Never suppress or filter GitHub's notifications in account settings: a notification that does arrive is a real signal, of a run nothing else covers or of an attribution leak to fix at its source. Reference instance: ph-ps (`AGENTS.md`, "Automations"; `scripts/check-automations` fails any workflow an event attributed to a person would start). Not yet compliant (TODO): The Hinge's "Daily issue" runs, attributed to Pablo (notified 2026-10-23).

Validity rule (2026-10-09): an alert states only what is true when it is sent. A source that fails to deliver keeps no findings for later; its next run checks afresh and reports only what still holds, and the failed delivery is reported by the withheld heartbeat. A check does not report a condition that the Mac being off or logged out explains (a job not yet due since load, a heartbeat that could not have been refreshed).

Nothing to do, no alert (Pablo, 2026-11-05): a failure that a fallback fully covers, and that leaves Pablo nothing to do, is logged, not alerted, and the log must persist so its frequency can still be checked. Alert on the same source's other failures, which may mean it has changed for good, and on the fallback failing. First instance: the supervisor's Substack read, whose HTTP 429 (Substack throttles Cloudflare's shared egress) alerted on two days of three while `issue.json` and the run's own read covered it. Sibling: The Hinge's feed relay, which serves its last good copy on the same 429 (`relay/worker.js`). The shared service's own alerts were swept on 2026-11-08 (noise rules below); The Hinge's pool-ended alert ("the run carried on") is still sent and is a candidate (TODO).

Paused jobs (Pablo, 2026-11-09): a job its owner has deliberately stopped but kept installed is marked paused wherever it is monitored. The mark records since when, why, on whose decision and a review-by date. Never leave a paused job alerting daily, and never silence it by removing its monitoring. Until the review date a paused job is reported as information only. It alerts once that date passes, or if it is found loaded or running while marked paused. Resuming the job removes the mark. First instance: the launchd registry's `paused` field (`~/repos/launchd/README.md`), for TangoDB's nightly rebuild and trigger, paused on 2026-11-08. A launchd job installed without `--load` is paused the same way until it is loaded (`decided_by` names the installer; loading it removes that pause only), so a staged install never alerts (added 2026-11-09 after android-org-sync, installed unloaded, failed the next audit). The heartbeat Worker has no paused state yet. Its `activeUntilUtc` covers planned ends, not pauses (TODO: add one when a Worker source is first paused).

Noise rules (Pablo, 2026-11-08, after a review of 239 Telegram messages in which most left nothing to do):
- One cause, one message: a detected outage is held one cron tick (15 min) and then sent together with every other outage pending at that moment. An outage that ends within the hold sends nothing and is logged. Monitors that fail together by construction share a config `group` whose hint replaces theirs (the three mail syncs: Emacs or mu4e stopped).
- Recoveries are sent silently (Telegram `disable_notification`), grouped like outages.
- A repeated immediate alert (same source and kind, same text apart from numbers and links) is sent once and then logged for 7 days; a changed text is sent.
- A failure that a supervisor still retries is logged, not sent (`?covered=supervisor` on `/alert`; the supervisor's last resort is the alert), and so is a dispatch GitHub accepted. A supervised deadline monitor still alerts 30 minutes after the last resort, as an independent backstop should the supervisor fail.
- Whatever is logged instead of sent is kept in the monitor's Durable Object and shown under `logged` in `GET /status`, so frequencies stay checkable.

## The service

`~/repos/launchd/heartbeat/` (README there): a Cloudflare Worker on the personal account, independent of the Mac and of GitHub, delivering on Telegram (@PablosNotificationBot) or Gmail SMTP.

- **Monitors** live in `src/monitors.ts`, one Durable Object each. Two rules:
  - `staleAfterMs`: alert when no heartbeat has arrived for that long (Mac jobs);
  - `dailyDeadlineUtc`: alert when no heartbeat dated today has arrived by that time. It is armed from deployment and alerts again on each missed day (daily jobs, CI).
- **Routes**: `POST /heartbeat/NAME` after each success; `POST /alert/NAME` (text body) for an immediate failure alert, with `?covered=supervisor` when the monitor's supervisor retries it; `POST /notice/NAME` for news that is not a failure; `GET /status`.
- **Tokens**: `HEARTBEAT_TOKEN` (Mac client, every route). A source outside the Mac gets a monitor-scoped token (`tokenSecret` in the monitor config, listed in `deploy.py` `MONITOR_TOKEN_SECRETS`, kept in the personal `Automation` vault) that covers only its own heartbeat and alert routes.
- **Verify live** with its verification mode (`deploy.py --var VERIFICATION_MODE:true`, `/verify/stale`, `/verify/reset`), then redeploy without it.
- **Supervisor** (2026-11-02, the second trigger of `scheduling.md`): a monitor may carry a `supervisor` config (`src/supervisor.ts`). At each checkpoint it reads the job's outcome from its own source of truth and the workflow's runs; if the outcome is missing and nothing is running, it dispatches the workflow as a GitHub App (var `GITHUB_APP_ID`, secret `GITHUB_APP_PRIVATE_KEY` from the personal `Automation` vault, listed in `deploy.py` `SUPERVISOR_SECRETS`), and at its last-resort time it alerts with what Pablo can do by hand. Verify a deployment with `deploy.py --var SUPERVISOR_PROBE:<new value>`, which dispatches one `probe=true` run, then redeploy without it.

## Adding a source

1. Add the monitor (and a scoped token if the source is not the Mac), with a test, in `~/repos/launchd/heartbeat`; run `npm run verify`; deploy.
2. The source sends a heartbeat after real success, judged by its outcome, not merely by the process exiting 0. On failure it calls `/alert/NAME`.
3. Do not rely on GitHub's own failure email: it did not arrive on 2026-10-06 or 2026-10-08.
