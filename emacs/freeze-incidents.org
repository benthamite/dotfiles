#+title: Emacs freeze incidents

Running record of Emacs freezes and slowdowns: what each investigation found,
what was changed, and what is still open. The =emacs-freeze= skill reads this
before diagnosing, so that a session does not re-propose a remedy already
tried. Append one entry per investigation; update the open items and
the "Already tried" list in place.

* Evidence sources

- Watchdog: =bin/emacs-server-watchdog=, run each minute by launchd.
  - Outage/recovery log: =~/Library/Logs/emacs-server-watchdog.log= (local
    time).
  - Per-minute samples: =~/Library/Logs/emacs-server-watchdog.samples.jsonl=.
    Fields include probe result and failure kind, state-file age, GC count and
    seconds since the previous sample, Emacs footprint, swap, top processes.
    =time= is epoch seconds; convert with jq =strflocaltime=, not =strftime=
    (UTC).
- State file =~/.cache/emacs-server-state.json=, written every 5 s by
  =simple-extras-server-state-mode=. Stale means timers are not running.
- Display sleep/wake: =pmset -g log=. Several outages ended seconds after the
  display woke, i.e. Emacs froze while Pablo was away.
- Stacks: since 2026-10-10 the watchdog runs =/usr/bin/sample= when a probe
  fails or a minute has 30+ GCs (at most every 5 min) into
  =~/Library/Logs/emacs-server-watchdog.stacks/=; the sample line's
  =stack_file= names the report. It finishes 20-80 s after the run.
  Native-compiled Lisp shows as =F<hex>_<name>_N= symbols.

* Already tried (do not re-propose without new evidence)

- Restarting Google Drive (2026-10-07): footprint fell from 23 GB to 0.4 GB,
  but was back at 15 GB within about an hour and at ~23 GB by 10-09. A restart
  is not a fix: the memory refills within ~20 min of every start (see the
  2026-10-10 Drive finding below).
- Backblaze exclusion rules (2026-10-07): stop index growth, do not shrink
  the existing 5.5 GB =bzfileids.dat=.
- =gcmh-low-cons-threshold= raised to 128 MB (2026-10-07, =351180ef6=):
  outages continued (30 on 10-10).
- SIGUSR2 against a sentinel loop (2026-10-13): breaks the chain only
  briefly while the code that feeds it stays loaded.
- =emacsk= repeatedly: stacks nested debuggers and leaves =debug-on-quit= on
  (2026-10-06). Press it once.

* Incidents

** 2026-10-17: all-day outages under host starvation (investigation, no change)

- 16 outages 05:02–16:37, the longest 13:31–14:45 (refused). At 16:35 swap
  was 25.6/26.6 GB, free RAM ~70 MB and load 150–200; the watchdog itself
  wrote no sample from 16:17 to 16:27. Google Drive still ~23 GB.
- Emacs 4855 was not stuck in Lisp. Two 5 s samples at 16:35 showed the main
  thread idle in =read_char=; its CPU time was flat for a minute, then the
  pending clients completed and =(emacs-pid)= answered in 0.4 s at 16:38.
  Recursion depth 0. The day's watchdog stacks got only 34–81 of ~4,400
  samples each (barely scheduled), showed no hot Lisp, and took up to 12 min
  to write.
- GC: 3438 GCs, 3725 s total in 4 days (~1.1 s each), consistent with GC over
  a swapped heap.
- Extra load at the time: the Claude session 80969 (tangodb
  =listening-20261016= worktree) ran a 9-worker Python job spawning =fpcalc=
  from 16:08, which matches the 16:10–16:37 load rise; an =agent-log= summary
  worker (Emacs --quick, 1 GB, ~90% CPU for 8+ min); Backblaze =bztransmit=
  3.2 GB RSS. These add to the pressure; the morning outages predate the
  =fpcalc= job, so the chronic cause is still memory (see Open).

** 2026-10-12 23:19 → 10-13: agent.el status-query loop (fixed in agent =5bb959a=)

- Server unanswered from 23:19, refused from 00:47 (listen backlog full);
  Emacs 24375 at 100% CPU throughout. Not memory: swap 17 GB, load ~11.
- 08:49 stacks: ~500+ nested =kill-buffer= → =delete-process= →
  =status_notify= → sentinel → =kill-buffer= frames (sampler truncates the
  root), with =claude-code--find-all-claude-buffers= and
  =generate-new-buffer-name= as leaf work. Emacs spawns a =claude= child
  about once a second; open pipes swing between ~340 and ~1300.
- Source: =agent-claude--query-agents-status= / =--finish-agents-query=
  (agent.el =2af0543=, 2026-10-11). The sentinel kills the query's buffers,
  and that runs other exited queries' sentinels inside it; it also starts the
  rerun query from inside the sentinel. Inferred: a self-feeding nesting loop.
- 00:53 stacks: a timer's =make-process= (the scheduled query) signalled a
  file error, =debug-on-error= opened a debugger, and timers inside it
  repeated the failure. =get-process= scanned a huge process list and
  =generate-new-buffer-name= a huge buffer list, so query buffers and
  processes were leaking. The exact errno was not captured; fd exhaustion
  is a guess.
- Recovery: SIGUSR2 at 09:54 unwound the chain into nested debuggers
  (timer =make-process= failing to create a pipe), but the server stayed
  unanswered and the loop resumed within 4 min. SIGTERM was approved;
  the agent's permission classifier blocked it, so it was handed to Pablo.
- Fix: agent.el finishes queries from a timer, never inside the sentinel;
  an exited but unstored query blocks duplicates; a query that cannot start
  becomes an error result (3 regression tests fail before, pass after).
  Committed and pushed as agent =5bb959a= on 2026-10-13 by a later
  session, the diagnosing one having ended with the frozen Emacs. Checked
  live: a query that cannot start stores an error and leaks no buffer.
  The nesting loop itself was not reproduced live.
- The 10-11/10-12 outages started the day this code landed; the earlier
  ones (10-06 to 10-10) predate it and have other causes.

** 2026-10-10: Google Drive memory (investigation, no change)

- The main "Google Drive" child process holds it: 22 GB footprint, 22.3 GB
  swapped, 100 MB resident. Malloc 13.5 GB in 16.9M live allocations, plus
  11.2 GB of 160 KB "Foundation" regions; not fragmentation.
- It fills in ~20 min after each start, during DriveFS's startup scan of
  ~355k mirrored items ("ScanCloud Generated 354928 download events"), then
  grows only ~0.5 GB/day. Inferred: ~63 KB retained per mirrored item.
- Biggest mirrored trees under =~/My Drive=: Music 130k items, Apps 56k
  (Zotero Library backup ~14k), Websites 34k, Dictionaries 34k, library-pdf
  17k. =~/My Drive/repos= (3.6k, agent state) also violates the no-code-in-Drive
  rule.
- Drive for desktop 132.0.0.0; no acknowledged Google issue, only anecdotal
  reports of Mirror mode using 20-30 GB.

** 2026-10-10: two freezes late morning (BST)

- 11:24–11:28: server timed out, then refused connections; single GCs of
  3.6 s and 10 s, load 52–55, swap 19 GB. Display was asleep 11:23:35–11:27:52;
  recovery came 3 s after wake. Inferred: GC over a partly swapped heap under
  host memory pressure.
- 11:43–11:47: 133 GCs (41 s) in one minute, 53 (17 s) in the next, each
  ~0.3 s. Only one failed probe, so this was constant pausing rather than a
  blocked server. No other minute in the 7-day samples had 30+ GCs. Trigger
  unknown.
- Earlier the same day: 07:13–07:55-ish a 45 min block with stale state, and
  08:35–09:07 outages every ~5 min. =mu4e-update-interval= is 300, but the
  mu4e update path is asynchronous, so that link is weak.
- "Quit emacsclient request" in *Messages* only means Pablo's C-g landed in
  an agent hook's emacsclient request queued behind the stall; the hooks are
  not implicated. The =minibuffer-quit= backtrace in mu4e's search prompt
  came from =debug-on-quit= being on, and shows Lisp idle at the prompt.
